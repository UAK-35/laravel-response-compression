# AGENTS.md — Canonical Rules

This is the **single source of truth** for AI agents and development tools working in this
repository. Every other agentic file — `CLAUDE.md`, `GEMINI.md`, `.trae/TRAE.md`, the rules under
`.cursor/`, `.continue/`, `.junie/`, `.kiro/`, `.windsurf/` and `.github/` — points here and restates
nothing, so a rule is edited in exactly one place and cannot come to mean two things.

**Skills and custom agents live only under `.agents/`:**

- Skills: `.agents/skills/<name>/SKILL.md` (authored in `.skills/<name>/`, generated by
  `python .skills/_sync.py` — the source is the source and the target is generated)
- Custom agents: `.agents/agents/<id>.md`
- Commands: `.agents/commands/<name>.md`

---

## 0. Hard rule — no parent-folder agentic config

**Never load agentic configuration (rules, skills, or custom agents) from a parent folder.** Only
this repository root is authoritative for this package.

This checkout is developed inside a larger workspace whose root also carries `AGENTS.md`, `.agents/`,
`.claude/`, `.trae/`, `.kiro/` and more. Those describe a Laravel application and **do not apply
here** — not its layout, not its database rules, not its deploy or push runbooks. The parent's
configuration is not read, not extended, and not pointed at:
`python .agents/verify.py` fails on any agentic file that names a path outside this repository.

## 1. What this package is

`uak35/laravel-response-compression` — a **Laravel middleware package** that compresses a response
body with gzip, brotli or zstd according to `Accept-Encoding`, and a config file that decides when
it is allowed to.

| | |
|---|---|
| Kind | library (`composer.json` `"type": "library"`) |
| Runtime | PHP `^8.4`, `illuminate/http` + `illuminate/support` `^12.4.1\|^13.0` |
| Required extensions | `ext-zlib`, `ext-brotli`, `ext-zstd` |
| Dev tools | Pest 4 (with Testbench 11), PHPStan at max, Rector, Pint, all pinned to exact versions |
| Public surface | whatever `src/` exports, plus `config/response-compression.php` |
| Consumers | Laravel applications that install it — there is no app here to run |

There is **no `artisan`, no routes, no controllers, no database, no queue and no `.env`** in this
repository, and a skill or rule that assumes one is describing the wrong repository. Development
happens through Composer scripts, the gate in `bin/`, and the Pest suite.

Two consequences worth stating before anything else:

- **Everything in `src/` is public API.** A consumer upgrades on a semver promise, so a change to a
  signature, a config key's default or a class's namespace is a breaking change and is weighed as
  one by `bin/release.php` before it becomes a version.
- **`docs/` is not decoration.** Each record explains a decision the code cannot explain about
  itself (why `min_length` clamps, why a user agent is refused, why config is read once). A change
  that contradicts a record is a change to that record, in the same commit.

## 2. Environment & shell

| Item | Value |
|---|---|
| Project root | `__PACKAGE_DIR__` (a token — section 3 has the file it comes from) |
| Windows shell (mandatory) | PowerShell 7, by the token `__PWSH_EXE__` |
| Linux shell (mandatory) | `bash` |
| PHP binary | `__PHP_EXE__` — named by `.agents/machine.local.json`, and decided by `.agents/php-bin.sh` |
| Package manager | `composer`, or `"$(python .agents/render_local.py --value __PHP_EXE__)" composer.phar <script>` where `composer` is not on `PATH` |
| How a command reaches PHP | the token, resolved per command. Most commands name none at all: Composer runs a script under the interpreter already running it, so `composer checks` and `composer test` are interpreter-free |
| Search utility (mandatory) | `rg` (ripgrep); `git grep` where a shell has no `rg` |

Two of those are **tokens rather than paths**. This machine's PHP, PowerShell and package directory
are named once, in the gitignored `.agents/machine.local.json`, and `python .agents/render_local.py
--value __PHP_EXE__` prints the value when a command needs it spelled out:

```bash
"$(python .agents/render_local.py --value __PHP_EXE__)" bin/checks.php --staged
```

A command a skill or an agent hands over **carries that rendering, not the placeholder**. The four
commands in section 13 that need an interpreter render it from `.agents/machine.local.json` in the
line itself; `__PHP_EXE__ bin/checks.php --staged` is a line a reader has to substitute before
anything runs, which is not a command. The token belongs where it is being defined - the `PHP binary`
row above, and the token table in section 3 - and in prose about resolving it; in front of a program
it is a placeholder pretending to be a command.

Nothing else in this repository writes an interpreter down, and nothing else decides one either.
`.agents/php-bin.sh` is the one place that answers "which PHP", in this order: `$RESPONSE_COMPRESSION_PHP`,
then `.agents/machine.local.json` read through `python .agents/render_local.py --value __PHP_EXE__`,
then `git config --get response-compression.php`, then `php` on `PATH`. `sh .agents/php-bin.sh --show`
says which rung answered about this checkout, and four things ask rather than deciding again:

- the **pre-commit hook**, which skips rather than blocking when no interpreter is found — a machine
  without PHP must not become a machine that cannot commit — and says so when a fallback answered;
- **CI**, which runs `sh .agents/php-bin.sh --matrix` to get the version it installs, so
  composer.json's `require.php` is not written into the workflow as a second copy of itself;
- **`bin/tool.php`**, which prints one line when the tool is about to run under an interpreter other
  than the one this machine names — the vendor/bin failure one layer up;
- **`bin/coverage.php`**, whose header names both interpreters when they differ, because a floor
  recorded under one and measured under another is the first thing to rule out when one moves.

A composer script runs under `PHP_BINARY` and names none, and every tool in `bin/` runs a vendor
entry file the same way (`.agents/toolchain.json` has the rule). `python .agents/verify.py`'s
`interpreter` step refuses a second copy of any of the four, and `tools` asks the resolver to prove
its own ladder — four rungs is four chances to answer something else, and the shell file is what
`Tests\Support\PhpBinary` and the hook both believe.

An interpreter written **in front of** a command is refused too, and it is the same failure as a
`vendor/bin` shim one word further in: the shim is a second interpreter because it runs whichever
`php` is first on `PATH`, and a command written with one in front of it says the same thing with the
shim left out. So no command in the layer may be written that way — the four that need an interpreter render it out of
`.agents/machine.local.json` in the command itself, `@php` is left alone because it is Composer's own
word for the interpreter it is already under, and one program is excused by name because it cannot be
written any other way: `bin/bootstrap.php` runs before there is a machine file for the answer to come
from. **This rule is decided per platform and declared that way**, because an interpreter is spelled
differently on each: Windows carries an extension on the name (`php.exe`, `pwsh.exe`), reaches a
shell of its own (`powershell`, `cmd`) and calls a program `.php`, `.ps1`, `.bat` or `.cmd`, while
Linux and macOS spell PHP as `php` and a program as `.php`. Those two are the same answer today and
are kept apart anyway — a Linux rule that started refusing `bash -c "<line>"` would be refusing the
way every command is run there by mandate. `verify.py`'s `toolchain` step reads the layer for it and
names the platform in the finding, and `--selftest` plants one for every platform's rule at once by
writing it where a session copies a command from.

Wrap every command in the mandated shell for the platform:

```bash
# Windows
"__PWSH_EXE__" -Command "<command>"

# Linux
bash -c "<command>"
```

**Path mandate.** No file a commit would carry may contain a drive path, a home directory or a
network share. Two guards enforce it — `tests/Unit/Support/MachinePathsTest.php` for the machine a
path names, and `tests/Unit/Support/RepoEscapesTest.php` for a relative path that climbs above this
repository — and neither has an allowlist you can add yourself out of: a path that is genuinely the
same on every machine (`C:/Windows/…`, `/home/runner/…`) is excused **in the detector**, with the
reason written beside it. Write `__TOKEN__` instead.

## 3. Session startup

Load, in order:

1. `AGENTS.md` (this file)
2. `.agents/README.md` (skills, custom agents, commands — the index of everything loadable)
3. `.trae/TRAE.md` (the anchor a TRAE session starts from)
4. `GEMINI.md` (team-shared notes; its generated `SKILLS-IMPORT` block lists every skill)

Before finishing any work, run the check — read-only, exit 1 when something is inconsistent:

```bash
python .agents/verify.py              # everything: the tools, the two path guards, the gate, the layer
python .agents/verify.py --package    # the tools and the two package checks, without the layer
python .agents/verify.py --layer      # the layer alone, with no PHP in it - what the hook runs
python .agents/verify.py --only=tools # one step
python .agents/verify.py --fix        # repair what a generator owns, then re-check
python .agents/verify.py --selftest   # prove each step still reports a planted fault
```

It has two halves. The `tools` step **runs programs**: PHP and its version against the pin, the
`ext-*` requirements in `composer.json`, a coverage driver for the floor, composer, Python,
PowerShell 7 on Windows, git, every tool in `bin/tool-paths.php` asked to start through
`bin/tool.php`, whether the hook below is enabled in this clone, and whether there is a `vendor/` at
all. The ten layer steps **read files**: this directory against itself, the pointer files, each
skill target against the source it was generated from, the rendered command table, the settings files
against their templates, and the tokens. The `tools` step also keeps what it asked - the tool, the
version it reported, the pin it was held to, and whether it ran at all - and prints it as one table
when the run ends, so a red run says which part of the machine moved without the reader matching a
finding's wording back to the tool it is about.

Neither half replaces the gate: `composer checks` and `composer test:unit` are what decides whether
the package is right, which section 5 covers. `guards` and `gate` are steps of this program that run
those two readings rather than repeating them.

### Machine-local settings — never committed

Absolute tool paths live in exactly **one** local file, `.agents/machine.local.json`, which is
gitignored. Everything committed refers to a path through a `__TOKEN__` instead:

| Token | Meaning |
|---|---|
| `__PHP_EXE__` | absolute path to `php.exe` |
| `__PHP_DIR__` | the directory containing `php.exe` |
| `__PWSH_EXE__` | absolute path to `pwsh.exe` |
| `__PACKAGE_DIR__` | absolute path to this package — the repository root |

```bash
python .agents/render_local.py --init    # asks for the paths, writes machine.local.json, renders every settings file
python .agents/render_local.py           # render every settings file from it
python .agents/render_local.py --check   # report unresolved tokens, write nothing
python .agents/render_local.py --value __PHP_EXE__   # answer a token for prose or a shell
```

Each settings file a tool reads (`.trae/settings.json`, `.trae/settings.local.json`,
`.kiro/settings/local.json`) is committed as its `.example` template and written from it; the
rendered file is gitignored, and `verify.py` reports a rendered file that has drifted from what its
template would produce rather than overwriting it — in any checkout, not only a git repository,
because the comparison reads two files and asks git nothing.

## 5. The gate

`composer checks` is eleven checks in one process, and it is the same gate a tag is cut behind:

| Key | What it proves |
|---|---|
| `syntax` | every PHP file parses |
| `ast` | the same files parse as an AST (`nikic/php-parser`) |
| `schema` | `composer.json` validates strictly |
| `platform` | every platform requirement is installed — where a missing `ext-brotli` is reported as a build problem rather than as a test failure |
| `toolchain` | the machine's own question, asked of `.agents/verify.py`: this PHP answers the pin in `.agents/toolchain.json`, it carries the extensions `composer.json` requires, a coverage driver is loaded, and every tool in `bin/tool-paths.php` still starts through `bin/tool.php` — so a wrong PHP or a missing extension is a line in the gate rather than a test that could not run |
| `agentic` | the layer this repository keeps about itself, asked of `.agents/verify.py`: the canonical rules and their sections, the pointer files, the index, the generated skill targets, the rendered command table, the interpreter rule, the tokens and the skill descriptions — and, underneath them, `--selftest`, which plants one fault per reading in a copy of the layer and requires the reading to name it, so a step that has stopped checking fails the gate instead of passing quietly |
| `yaml` | the workflow YAML, this package's own included |
| `phpstan` | static analysis at max level |
| `pint` | code style, in test mode |
| `rector` | the refactorings Rector would make (`--dry-run`) |
| `tests` | the Pest suite |

The tools behind five of those rows — `yaml-lint`, `phpstan`, `pint`, `rector` and `pest` — are
`bin/tool-paths.php`'s, with the version this package pins each one at and one line saying what it
is for, and `bin/checks.php --list` prints that table: the gate describing itself out of the one
place those facts are written down. The row above says what a check *proves*, which is a fact about
the check rather than about the tool it runs — `syntax`, `ast`, `schema` and `platform` run no tool
in that manifest.

```bash
composer checks                          # a workstation: a missing tool is a skip
composer checks -- --require-all         # CI and a release: a missing tool is a failure

# __PHP_EXE__ is this machine's PHP, rendered from .agents/machine.local.json in the line itself:
"$(python .agents/render_local.py --value __PHP_EXE__)" bin/checks.php --list    # the eleven, each one's skip condition, and the tools the manifest pins
"$(python .agents/render_local.py --value __PHP_EXE__)" bin/checks.php --staged  # staged files only — what the pre-commit hook runs
```

**The gate is not the cover.** `composer checks` runs Pest without a coverage driver on purpose, so
that it works on a machine that has none. The floor is `composer test:unit` — every `src/` file at
100.0%, and a ratchet per program in `bin/` — and CI runs it as its own step. A change that lowers a
floor fails there, and `bin/coverage.php` says which PHP and which driver produced the number.

### The pre-commit hook

`.githooks/pre-commit` runs `bin/checks.php --staged` — syntax, style, the tests that cover the
staged files (out of `tests/Support/TestMap.php`, so a change to a release program runs the release
rails) and the links between the docs, which are the things a commit can break on its own. Enable it
once per clone:

```bash
git config core.hooksPath .githooks
```

It takes the interpreter from `.agents/machine.local.json` first — through
`python .agents/render_local.py --value __PHP_EXE__`, so the same value every settings file is
rendered from and the same one `python .agents/verify.py` asks about — then from
`$RESPONSE_COMPRESSION_PHP`, then from a `response-compression.php` entry in `.git/config`, then
from `php` on `PATH`. The last three are older ways of naming an interpreter and survive only so
that a clone which has not run `python .agents/render_local.py --init` still commits; when one of
them is what answered, the hook **says so**, because a check run under an interpreter nothing else
in the repository agreed to is the failure that leaves no trace. It **skips rather than blocks**
when there is no PHP at all: a machine without PHP must not become a machine that cannot commit. It also runs
`python .agents/verify.py --layer` when an agentic file is part of the commit, with the same
skip-when-absent rule — the layer subset, because the commit is already running the staged half of
the gate and the full run would ask the same questions again.

## 6. Testing

- Pest 4, under `tests/Unit/`, with `tests/Pest.php` carrying the shared helpers. There is no
  `tests/Feature/`: nothing here answers a request on its own, so a test is a unit test even when it
  builds a whole response through Testbench.
- The suite is the specification. A behaviour change adds or updates a test that fails without it —
  and a test that reports nothing on a tree with something wrong in it is worse than no test, which
  is what section 7 is about.
- Prefer the real object to a mock: the middleware is pure enough to drive with a request and a
  response, and Testbench builds the container a host app would.
- A test that spawns a program (anything measuring the `bin/` scripts) has to be reachable as a
  child process — `tests/Support/collect-coverage.php` is the collector those children run under.

## 7. The guards, and the rule that protects them

`docs/guards.md` is the index of every guard this package keeps, what each one catches, and which
ones were considered and refused. It is not a summary written after the fact: `GuardIndexTest`
reads the table as a claim about two directories — every row links a file that exists, **every file
in `tests/Support/` is named on that page**, and **every test in `tests/Unit/` declares itself a
`guard` the table links or a `test` the table is not about** — so a new guard costs one line of the
index and one line in its own test's header, and a row that resolves nothing fails.

The two lists of files below that table are **rendered rather than written**. A file in
`tests/Support/` carries one line in its own header — `@guards-index` with either `reading` or
`support` — and the first sentence of that header is the words beside its row; `bin/index.php` writes
the two tables from that, and `bin/index.php --check` is what the suite asserts. A file that
declares nothing, or declares a list the page does not have, is refused by name — the two lists
cannot come to disagree with the directory, because the directory is where they come from.

The guard table's other side is the tests themselves, and it is written by hand rather than
rendered, because what a guard refuses is an argument. What is enforced is the link: a test says
`guard` in its own header and the table has to name it, and a test that says nothing at all is
refused rather than read as one of them. `bin/index.php --check` reports a guard the table has no
row for, and `GuardIndexTest` asserts on the same reading, so a guard cannot arrive with a test and
no row — from the reading side or the test side.

Two rules follow, and both are enforced rather than asked for:

- **A guard is added with its row** in `docs/guards.md`, a test in `tests/Unit/` whose header says
  `@guards-index guard`, and — when it has a reading of its own — a file in `tests/Support/` that
  says which list it is in. Then run `composer index` (or `bin/index.php`) to write the row.
- **A guard may not go quiet.** `tests/Support/MutationHarness.php` breaks this checkout one way at a
  time and requires the guard's own reading to *name* the break: a reading that stopped asking the
  right question answers with nothing both times, and an assertion on "something" would be answered
  by either state. A guard added to the index has to be mutated there or declined by name and
  reason, so the harness fails on a new guard rather than ignoring it.

## 8. Code rules

- `declare(strict_types=1);` in every file. Explicit parameter and return types; PHPDoc where a type
  cannot say it (`list<…>`, array shapes).
- PHP 8.4 is available and used: the typed class constants and readonly properties in `tests/Support/`
  are the house style, not an exception.
- One class per file, PSR-4 under `Uak35\ResponseCompression\`. `tests/` is autoloaded as
  `Uak35\ResponseCompression\Tests\`.
- Config is read through `src/Support/Config.php`, once, deliberately: `env()` never appears outside
  `config/`, and a value that cannot be read is refused rather than quietly replaced with a default.
- A comment earns its place by saying *why*. The house style is prose that argues for a decision;
  a comment that restates the line below it is noise, and the guards in `tests/Support/` are written
  in exactly that voice.
- Never edit `vendor/`.
- Style is Pint's (`pint.json`) — run `composer tidy` (lint, refactor, lint) rather than fixing style
  by hand, and let the second Pint pass judge what Rector rewrote.

## 9. Documentation records and the changelog

- **Every change to behaviour, tooling or docs carries a `CHANGELOG.md` bullet** under
  `## Unreleased`, in the section it belongs to, written in the file's voice: a bold sentence saying
  what changed, then the reasoning, in prose, naming the files and the commands involved. The
  changelog is read by consumers and by `bin/release.php`, which weighs a release by reading the
  commits since the last tag and the notes this file already holds.
- A `docs/` record exists for a decision that needs arguing: fourteen today, each linked from the
  README's design records section, each linked onward from its neighbours. A new one needs a README
  link — `DocsLinksTest` resolves every link in `README.md`, `CHANGELOG.md`, `RELEASING.md`,
  `PUSHING.md` and every `docs/*.md`, and notices a record nothing links to.
- A claim in a record is checked where it can be: `ConfigClaimsTest` reads the docblock beside each
  config key and the README's copy of it, so a key whose comment says it is read by something that
  stopped reading it fails there.

## 10. Releases and the two runbooks

A version is a tag, and Packagist publishes tags — not branches, not commits. The lane is
**`development`**, and every cut passes `--branch=development`, because `bin/release.php` defaults to
`main` and refuses a release anywhere it was not told to expect one.

```bash
composer release -- --weigh --branch=development            # what the tree adds up to; cuts nothing
composer release -- --weigh --dry-run --branch=development  # the same, with the notes printed
composer release -- --branch=development --push             # cut, write the notes, and push
```

- `RELEASING.md` — what a version *is*: the numbering, the prerelease lanes, what the releaser writes
  into the release commit, and how to do it by hand.
- `PUSHING.md` — where a tag goes, what authenticates, and the evidence table for both. Read it
  before believing a claim about the remote: it is re-verified claim by claim, and it says which of
  its rows were read rather than exercised.

Both are `export-ignore` in `.gitattributes`, so an installed package never receives them — which is
why nothing the package ships links to either.

## 11. Commits

- Commit **named paths**, never `git add -A`. This repository is developed beside other work, and a
  blanket stage is how an unrelated file joins a commit.
- A commit that changes behaviour carries its `CHANGELOG.md` bullet, its tests, and its `docs/` record
  if the change contradicts one. A commit that adds a guard carries its index row.
- The pre-commit hook is the gate's narrow half. If it stops a commit, fix the finding rather than
  reaching for `--no-verify`; if a commit is bypassed deliberately, say so in the message.
- Write the subject as an instruction in the imperative that says *why* the change is right, with the
  body carrying the reasoning a reader cannot reconstruct from the diff.

## 12. Skills, custom agents and this directory

Everything loadable lives in `.agents/`, and nothing loadable lives anywhere else — not
`.claude/skills/`, not `.codex/skills/`, not `.windsurf/skills/`.

| What | Where it is authored | Where it is read from |
|---|---|---|
| Skill | `.skills/<name>/skill.yaml` + `instructions.md` | `.agents/skills/<name>/SKILL.md` (generated) |
| Custom agent | `.agents/agents/<id>.md` | the same file |
| Command | `.agents/commands/<name>.md` | the same file |

```bash
python .skills/_sync.py            # regenerate .agents/skills/, the GEMINI.md imports, the Windsurf pointers
python .agents/verify.py           # prove the layer is consistent
```

`.agents/README.md` is the index: every skill, agent and command has a row there, and `verify.py`
fails when one does not — a skill that loads but cannot be found by reading the index can only be
found by somebody who already knew it existed.

`.agents/toolchain.json` is the one place a command or a tool pin is written down; the table below is
rendered from it, and `verify.py` refuses a restatement of any of them elsewhere.
